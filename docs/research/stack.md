## ⚠️ Read first: the Cart Transform "one line" assumption

Assumption under test: *"a non-Plus merchant can use a Cart Transform merge to show frame+lens+upgrades as one line."*

| Claim | Verdict | Evidence |
|---|---|---|
| `linesMerge` is available on non-Plus plans | **Mostly yes, but check at runtime.** The docs put no Plus restriction on `linesMerge` or `lineExpand`. Only `lineUpdate` is restricted. Eligibility is per shop, so query `shop.features.cartTransform.eligibleOperations.mergeOperation` and `shop.features.bundles.eligibleForBundles`. | Cart Transform API: https://shopify.dev/docs/api/functions/latest/cart-transform ; CartTransformEligibleOperations: https://shopify.dev/docs/api/admin-graphql/latest/objects/CartTransformEligibleOperations ; BundlesFeature: https://shopify.dev/docs/api/admin-graphql/latest/objects/BundlesFeature |
| Public apps with functions work on any plan | **Yes.** "Stores on any plan can use public apps that are distributed through the Shopify App Store and contain functions. Only stores on a Shopify Plus plan can use custom apps that contain Shopify Function APIs." | https://shopify.dev/docs/apps/build/functions , https://shopify.dev/docs/api/functions |
| We can set an arbitrary price on the merged line (e.g. frame price + lens price + coatings) | **NO. This contradicts the assumption.** The merge `price` is a `PriceAdjustment` whose only field is `percentageDecrease`. The docs say: "`linesMerge`: The final price is the sum of the individual component prices, plus the adjustment, if present." A merge can only keep the sum of the component prices or discount it. It cannot add a surcharge or set a fixed price. | Cart Transform API, *Pricing adjustments* section; schema `input PriceAdjustment { percentageDecrease: PriceAdjustmentValue }` in https://github.com/Shopify/extensions-templates/blob/main/functions-cart-transform-js/schema.graphql |
| We can override the price or title of a single line (`lineUpdate`) | **NO on non-Plus.** "Only development stores or stores on a Shopify Plus plan can use apps with `lineUpdate` operations." The invalid scenarios add: "The shop is not on a Plus plan or a Development store plan." **Trap:** dev stores *allow* it, so it will work in development and fail in production on non-Plus stores. | Cart Transform API (note under *Use cases* and *Invalid scenarios*) |
| Every lens and upgrade can be a free-form option | **NO.** Every merged component must be a real cart line holding a real **product variant**, and the merge needs a `parentVariantId` (an existing variant that represents the bundle). Lens types, indices and coatings must exist as priced variants in the merchant's catalog, and the app must create and own a parent "bundle" product. | `LinesMergeOperation.parentVariantId: ID!` and `cartLines: [CartLineInput!]!` (Cart Transform API); error `parent_variant_not_found` |
| It shows as one line everywhere | **Partially.** Cart: yes, the parent line with `item_components`. **Checkout: "Checkout lines present bundle products as a group of lines."** **Orders: "Order lines return bundle components, with a reference to the bundle parent."** The merchant's order and the `orders/create` payload contain the **component lines**, not one opaque line. Title overrides also need theme support (`item.title`, and `line.title` in notification emails). | https://shopify.dev/docs/apps/build/product-merchandising/bundles ; Cart Transform API *Overriding images and titles* |
| Other constraints | Rejected when a **selling plan** (subscription, pre-order, try-before-you-buy) is on the line. Not supported by Create Order API, Order Edit or subscriptions. If any other app's `lineExpand` hits the same line, the merge is discarded. A store can have **one cart transform per app**, and cart transforms from all installed apps run. Images in overrides must be on Shopify's CDN. Requires the `write_cart_transforms` scope, and "the shop must have upgraded to Checkout Extensibility". | Cart Transform API (compatibility list, *Multiple operations*, *Errors*); cartTransformCreate: https://shopify.dev/docs/api/admin-graphql/latest/mutations/cartTransformCreate |

**Alternative worth evaluating: nested cart lines (no function needed).** Shopify supports parent and child cart lines, "This supports product add-ons, such as warranties, protection plans, and service fees, that attach to a parent product". You create them from the Cart AJAX API with `parent_id` or `parent_line_key`, or from the Storefront API `parent` field. Shopify renders the relationship in the cart (Horizon and Dawn based themes), checkout, thank-you page, order status page, order emails and **Admin order details**. Children are removed with the parent. Limitations: only one level of nesting, it can't be used with bundles, and **`linesMerge` on a nested parent or child is a no-op**. The docs show no plan restriction. With this approach the frame is the parent line, lens and upgrades are child lines, each child is a priced variant, and private `_properties` carry the prescription reference. The result is grouped rather than literally one line, but it keeps real prices, real SKUs and per-component order lines that a lab can fulfil. Sources: https://shopify.dev/docs/apps/build/product-merchandising/nested-cart-lines , https://shopify.dev/docs/apps/build/product-merchandising/nested-cart-lines/create-nested-cart-lines

The latest on npm is **4.0.2** (published 2026-11-06). 4.0.0 is a major release that loads **Polaris web components 2.x** (`polaris-2.js`, the "Admin Next" theme) by default. ## 3. Theme app extensions and app proxy

**App blocks vs app embed blocks** (https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration):
- **App block** (`"target": "content"`) is inline content that merchants place in a section through the theme editor. It requires an Online Store 2.0 JSON-template theme. It can use `autofill` dynamic sources such as the product on a PDP. This is the right choice for an "Choose lenses" button or panel on the product page.
- **App embed block** (`"target": "head" | "body" | "compliance_head"`) is injected before `</head>` or `</body>`. It works in vintage and OS 2.0 themes, is deactivated by default, and can be enabled through a deep link. It suits a floating or modal configurator, or a global script. It has no dynamic sources, only the global Liquid scope.
- `enabled_on` and `disabled_on` limit blocks to certain templates. `available_if` gates a block on an app-data metafield (for example the billing plan).
- **Limits:** all files in the extension **10 MB** (enforced). **30 blocks** (enforced). **Liquid 100 KB total** (enforced). **CSS referenced by the schema 100 KB compressed (suggested)**. **JS referenced by the schema 10 KB compressed (suggested)**. Locale files: 100 files, 15 KB each. Blocks can't render on checkout pages. There is no access to `content_for_header` or `content_for_layout`, and no access to parent `section` properties other than `id`. Schema JSON can't contain comments or trailing commas.
- **App Store rule:** "Your app must not reduce the storefront Lighthouse performance score by more than ten points." (Built for Shopify requirements). App Store requirement 5.1.1 says to modify themes only through theme app extensions. https://shopify.dev/docs/apps/launch/shopify-app-store/app-store-requirements
- **Shipping a Vite-built Preact bundle:** Shopify CLI does not compile theme app extension JS. Files in `assets/` are served as-is from Shopify's CDN through the `javascript`/`stylesheet` schema keys or `asset_url`. So we can build with Vite outside the extension and **output a flat file** (for example `lens-advisor.js`) into `extensions/<ext>/assets/`. Asset **subdirectories are not supported** (Shopify CLI PR discussion https://github.com/Shopify/shopify-cli/pull/1934; community thread https://community.shopify.com/t/where-to-store-source-files-for-theme-app-extensions/145235). This rests on forum and GitHub sources, not shopify.dev, so verify on the first `shopify app deploy`. Keep the source outside the extension directory. Budget: the 10 KB JS figure is only a suggestion, but the Lighthouse rule is enforced. The pattern is a tiny loader (≤10 KB) in the schema `javascript` key that lazy-loads the Preact configurator chunk on interaction, using `asset_url` to get the CDN URL.
- **App proxy** (https://shopify.dev/docs/apps/build/online-store/app-proxies):
  - `shopify.app.toml` contains `[app_proxy] url = "/proxy" prefix = "apps" subpath = "lens-advisor"`, so `https://<shop>/apps/lens-advisor/*` maps to `https://<app>/proxy/*`. This needs the `write_app_proxy` scope. **Only one proxy route per app.** Merchants can customise `prefix` and `subpath`, so read the `path_prefix` query parameter instead of hard-coding the path.
  - Storefront JS calls the backend with a same-origin `fetch('/apps/lens-advisor/...')`, because the request goes to the shop's domain. Shopify forwards the method and body, and adds `shop`, `logged_in_customer_id`, `path_prefix`, `timestamp` and `signature` to the query.
  - **Cookies are stripped** in both directions, and some other headers are stripped too.
  - The signature is a hex SHA-256 HMAC of the sorted, concatenated query parameters (excluding `signature`), keyed with the app secret. https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
  - In the template, `await authenticate.public.appProxy(request)` validates the request and returns `{ session, admin, storefront, liquid }`. `admin` and `session` are `undefined` if the shop hasn't installed the app. `liquid(body, { layout })` returns a Liquid response. https://shopify.dev/docs/api/shopify-app-react-router/latest/authenticate/public/app-proxy
  - Changes to `url` apply to all stores immediately. Changes to `prefix` and `subpath` apply only to new installs.

## 4. Cart Transform function

See the table at the top. Further facts:
- Operations: `lineExpand` (one line becomes components, at most 150 expanded items, with optional per-component `fixedPricePerUnit` or a percentage adjustment, not both), `linesMerge` (N lines become a parent variant, `percentageDecrease` only), and `lineUpdate` (price, title or image of one line; Plus or dev stores only; the price can't be negative; images are checkout-only and not persisted to orders). Maximum quantity is 2000. https://shopify.dev/docs/api/functions/latest/cart-transform (api_version 2026-10)
- The `lineExpand` error list includes `price_per_component_feature_not_available`, `title_feature_not_available` and `image_feature_not_available` ("not accessible for the given shop"). Some expand features may also be gated per shop. Rely on `eligibleOperations` at runtime.
- **Languages:** any language that compiles to Wasm. Shopify ships Rust and JavaScript templates and says "Rust is recommended and strongly preferred" / "strongly recommends Rust as the most performant language choice to avoid your function failing with large carts". The JS template (`functions-cart-transform-js`) uses `@shopify/shopify_function ^2.0.1`, Vitest and `@shopify/shopify-function-test-helpers`. https://shopify.dev/docs/apps/build/functions , https://github.com/Shopify/extensions-templates/tree/main/functions-cart-transform-js
- **Limits** (https://shopify.dev/docs/api/functions): Wasm binary 256 KiB; linear memory 10 MiB; stack 512 kB; **11 M instructions** for carts up to 200 lines (dynamic beyond that); input 128 kB; output 20 kB; input query 3000 bytes and cost 30; metafield values over 10,000 bytes are not returned; logs 1 kB.
- **Registration:** deploy the function extension, then call the Admin GraphQL mutation `cartTransformCreate(functionHandle: "<handle>", blockOnFailure: false)` once per shop, for example after install. `functionId` is deprecated in favour of `functionHandle` (2025-10+). It needs `write_cart_transforms`, and per the bundles tutorial also `write_products` and `write_publications`. https://shopify.dev/docs/api/admin-graphql/latest/mutations/cartTransformCreate , https://shopify.dev/docs/apps/build/product-merchandising/bundles/add-customized-bundle-function
- **Bundle parent product:** create it with `claimOwnership: { bundles: true }` and set `requiresComponents: true` on the parent variant so it can't be bought alone. Up to 150 components. Nested bundles are not supported. Once an app assigns components, only that app can manage them. (Same tutorial.)
- **Display:** cart shows the parent plus `item_components`; checkout shows a group of lines; orders contain the component lines with a reference to the parent. https://shopify.dev/docs/apps/build/product-merchandising/bundles

## 5. Line item properties

- Prefix a key with `_` to make it private. Private properties are "visually hidden at checkout, but are visible on the **Order details** page in the Shopify admin". They **are** returned by Liquid `line_item.properties` and the AJAX API: "To hide private properties on the storefront, you must modify the theme's codebase." https://shopify.dev/docs/api/ajax/reference/cart (section *Private properties and attributes*), https://shopify.dev/docs/api/liquid/objects/line_item
- Cart drawers: Dawn's `snippets/cart-drawer.liquid` loops `item.properties` and **skips keys whose first character is `_`**, and also skips blank values. It renders `/uploads/` values as links. https://github.com/Shopify/dawn/blob/main/snippets/cart-drawer.liquid. So public properties (for example "Lens: 1.67 High-index, Blue-light") show in the cart drawer of Dawn-family themes, and `_rx_id` stays hidden. Third-party themes vary.
- **Limits:** no official documented size limit was found (WebSearch on 2026-11-07, community threads only). Store a short `_rx_ref` (an opaque id) and keep the prescription in our DB. Never put PHI or prescription values in properties. Posting properties to `/cart/add.js` replaces the item's whole properties object.
- Properties don't change price. Pricing must come from variants (see the top section).

## 6. Billing

- **For a new public app, Shopify now steers you to "Shopify App Pricing"** (previously Managed Pricing). It is "the default way to charge merchants when it supports their pricing model". Plans are defined in the Partner Dashboard and Shopify hosts the plan selection page at `https://admin.shopify.com/store/:store_handle/charges/:app_handle/pricing_plans`. The docs say: "Don't call the Billing API's `appSubscriptionCreate` mutation or your framework's `billing.request` helper." Subscription status comes from the **Partner API** `activeSubscription(appId, shopId)`. Testing on dev stores is free, and there is a $0 private test plan. https://shopify.dev/docs/apps/launch/billing/shopify-app-pricing
- **Manual pricing (Billing API) still exists** "for existing Billing API integrations, one-time purchases, and pricing models that Shopify App Pricing doesn't support". In `@shopify/shopify-app-react-router`, configure `shopifyApp({ billing: { [PLAN]: { lineItems: [{ amount, currencyCode, interval: BillingInterval.Every30Days | Annual }] } } })`. Then `billing.require({ plans, isTest, onFailure })` checks and throws or redirects, `billing.request({ plan, isTest, returnUrl, trialDays })` sends the merchant to approval, and `billing.check`, `billing.cancel` and `billing.createUsageRecord` are also available. `isTest: true` prevents charges, and "test shops and demo shops cannot be charged". https://shopify.dev/docs/api/shopify-app-react-router/latest/apis/billing
- App Store requirement 1.2: all charges must go through Shopify App Pricing or the Billing API. https://shopify.dev/docs/apps/launch/shopify-app-store/app-store-requirements

## 7. Webhooks, compliance and protected customer data

- **Mandatory compliance topics** for App Store apps are `customers/data_request`, `customers/redact` and `shop/redact`. Declare them in `shopify.app.toml`:
  ```toml
  [[webhooks.subscriptions]]
  compliance_topics = ["customers/data_request", "customers/redact", "shop/redact"]
  uri = "/webhooks/compliance"
  ```
  The app must accept a JSON POST, **return 401 on an invalid HMAC**, return a 2xx to acknowledge, and complete the action within 30 days. Without these the app is rejected at review. https://shopify.dev/docs/apps/build/privacy-law-compliance
- `app/uninstalled` is already in the template's toml (handler `webhooks.app.uninstalled.tsx` deletes sessions). Keep webhooks **app-specific in the toml**, because the README warns that `afterAuth` with `registerWebhooks` does not update reliably.
- **Verification:** `authenticate.webhook(request)` returns `{ shop, session, topic, payload, admin }` and verifies `X-Shopify-Hmac-SHA256`, a base64 HMAC-SHA256 of the raw body keyed with the client secret. Dedupe on `X-Shopify-Webhook-Id`. **Timeouts: 1 s to connect, 5 s for the whole request.** Shopify retries 8 times over 4 hours. Queue the work and respond fast. https://shopify.dev/docs/apps/build/webhooks/verify-deliveries , https://shopify.dev/docs/apps/build/webhooks/best-practices
- **Protected customer data:** "Webhooks … that relate to a single customer or order" and Orders are protected. **Level 1** covers customer or order data *excluding* name, address, phone and email. **Level 2** covers data *including* any of those fields, and adds data protection reviews. For a **public app both levels "Require review"**. Request access in Partner Dashboard → API access requests. On dev stores you only need to select the fields, with no review. Unapproved fields come back redacted or `null`, with an `errors` entry. https://shopify.dev/docs/apps/launch/protected-customer-data
  - Implication: an `orders/create` subscription needs at least Level 1 (plus `read_orders`). Printing the customer's name or shipping address on a lab job ticket needs Level 2, which means a review. Design the MVP to work with Level 1, using the order number, line items and `_rx_ref`, and fetch PII only if approved.
  - The App Store requirements page has no special rule for medical or prescription apps (grep for "prescription|medical|health" on 2026-11-07 returned nothing). Prescription data is our own sensitive data, so handle it under our own privacy policy and the compliance webhooks (`customers/redact` must delete prescriptions).

## 8. Testing

- **Unit tests: use Vitest.** Shopify's own function templates use `"test": "vitest"` with `@shopify/shopify-function-test-helpers`. The app template ships no test runner, but it is Vite-based, so Vitest fits naturally.
  - `@shopify/shopify-app-react-router/test-helpers` exports `testConfig()`. Apply it with `Object.assign(config, testConfig())` when `SHOPIFY_TESTING` is set, which gives in-memory sessions and dummy keys. Use `testConfig({ sessionStorage })` for e2e against the dev DB. Source: package README, https://github.com/Shopify/shopify-app-js/tree/main/packages/apps/shopify-app-react-router
  - Cart Transform: run unit tests on the `run` function with JSON fixtures, run `shopify app function run` (the `preview` script) against captured inputs, and replay real dev-store runs that `shopify app dev` writes to disk. https://shopify.dev/docs/apps/build/functions/test-debug-functions
- **E2E: there is no official Shopify guidance.** Community consensus (https://community.shopify.dev/t/what-would-shopify-suggest-regarding-e2e-tests/31851 , https://community.shopify.dev/t/automated-ui-testing-of-shopify-app/8709 , https://community.shopify.com/t/using-playwright-to-test-shopify-app-admin-interfaces/638595) is that automating Admin login hits captchas and ToS limits, and saved storage state is fragile. Recommended split:
  - **Storefront (theme extension and app proxy):** run Playwright against a password-protected **dev store** storefront (enter the storefront password, no Admin login). Exercise PDP → configurator → `/cart/add.js` → cart drawer → checkout page assertions. This is the most valuable e2e test.
  - **Admin embedded UI:** test React Router loaders and actions directly with `testConfig()`, and keep a few manual or semi-automated smoke tests. Verify side effects through the Admin GraphQL API instead of the iframe DOM.
  - Packages: `@playwright/test` (1.65.0) and `vitest` (5.1.0) (npm, 2026-11-07).

## 9. Render + Neon (+ Prisma)

- **Prisma major version: stay on 6.19.x.** The template's `@shopify/shopify-app-session-storage-prisma@11` has peer dependency `prisma ^6.19.0`. **Warning:** npm's `latest` tag for `prisma` currently points to **8.0.0-rc.33** (registry dist-tags, 2026-11-07), and Neon's guide says the same ("The `prisma` package's `latest` npm tag currently points to a Prisma 8 prerelease"). **Pin `prisma@6.19.x` and `@prisma/client@6.19.x` explicitly.** Never run a bare `npm i prisma`.
- **Neon connection strings:** use the pooled string (host contains `-pooler`) for the app at runtime and the direct string for migrations. In **Prisma 6**, put `url = env("DATABASE_URL")` (pooled) and `directUrl = env("DATABASE_URL_UNPOOLED")` (direct) in `schema.prisma`. `directUrl` exists in Prisma ≥4.10. In Prisma 7+, `directUrl` was removed, and the CLI URL moves to `prisma.config.ts` (or `prisma7.config.ts` in 7.10+). Sources: https://neon.com/docs/guides/prisma ; context7 `/prisma/web` (blog "from-local-to-production-with-prisma-postgres", docs "switch-to-prisma-postgres/from-neon").
- Change `provider` from `sqlite` to `postgresql` and regenerate migrations, because the SQLite migrations in the template won't apply.
- **Cold starts:** Neon computes scale to zero and "take a few seconds to wake up". Add `connect_timeout=15` to the connection string (Neon guide). Combined with Shopify's **5 s webhook timeout**, that is a real risk. Either disable scale-to-zero on the production branch, or ack webhooks instantly and enqueue.
- **Pooler limits:** the pooler rejects `search_path` startup options (use the default `public` schema), and it breaks `LISTEN/NOTIFY` (see job queue, §10).
- **Render:**
  - The template Dockerfile works with Render's Docker runtime. Render's Shopify guide (https://render.com/docs/deploy-shopify-app) is **stale**: it still says "Remix (recommended)". The env vars still apply: `SHOPIFY_APP_URL` set to the onrender URL, `NODE_ENV=production`, plus `SHOPIFY_API_KEY`, `SHOPIFY_API_SECRET` and `SCOPES`.
  - Render warns that local files (SQLite) are lost on deploy, so use Postgres.
  - The **free plan spins down** and "might take up to a minute to spin back up". That is incompatible with webhook and app-proxy latency, so use a paid instance for production.
  - The `docker-start` script runs `prisma migrate deploy` on every boot. It must use the **direct** URL, which Prisma 6 handles automatically through `directUrl`.
  - Run the job worker as a separate Render **Background Worker** from the same image, or in-process for the MVP.

## 10. Libraries (recommendations)

- **Email:** `resend` (6.37.0). Call `resend.emails.send({ from, to, subject, html|react|text, attachments: [{ filename, content: Buffer|base64, contentType? } | { path: url, filename }] }, { idempotencyKey })`. The limit is 40 MB per email. It returns `{ data: { id }, error }` and does not throw on API errors. context7 `/resend/resend-node` (create-email-options.interface.ts).
- **S3:** `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` (3.1164.0).
  - Presigned PUT: `getSignedUrl(s3, new PutObjectCommand({ Bucket, Key, ContentType, ServerSideEncryption: "aws:kms", SSEKMSKeyId }), { expiresIn })`. By default the SDK does **not** hoist `x-amz-*` headers, so the browser must send `x-amz-server-side-encryption` and the KMS key-id header exactly. Alternatively, pass `hoistableHeaders: new Set([...])` to put them in the query string. Source: context7 `/aws/aws-sdk-js-v3` (s3-request-presigner README).
  - Simpler option: set **bucket default encryption to SSE-KMS** (with a Bucket Key) and omit SSE parameters from the presigned URL. Since 2023-01-05, S3 applies SSE-S3 to all new objects at minimum, and it can't be disabled. https://docs.aws.amazon.com/AmazonS3/latest/userguide/default-encryption-faq.html
  - Recommendation: bucket default SSE-KMS, block public access, presign GET for downloads with a short expiry.
- **PDF: pick `pdfkit` (0.20.2, released 2026-08-30).**
  - It is pure Node with streaming output, embeds TTF fonts (`registerFont` from a path or buffer) and has a built-in `doc.table()` API that suits job-ticket layouts. context7 `/foliojs/pdfkit`.
  - Rejected `pdf-lib`: last release 1.17.1 on **2021-11-06** (unmaintained, and it is better for editing existing PDFs).
  - Rejected `@react-pdf/renderer` (4.9.0): it pulls a React and layout engine into the server and the worker for a simple fixed-layout ticket. That is heavier, though acceptable if the team wants JSX templates.
- **Job queue: pick `pg-boss` (12.38.1).**
  - It runs on Postgres (13+) and Node ≥22.12, which matches the template's Node floor. It **polls by default**, and `useListenNotify` is opt-in and off by default. The docs state LISTEN/NOTIFY does **not** work through PgBouncer in transaction mode and that pg-boss "continues polling only". So it works on Neon's pooled URL, or better on the direct URL for the worker. context7 `/timgit/pg-boss`.
  - Rejected `graphile-worker` (0.18.0): it uses LISTEN/NOTIFY **on by default with no option to disable**, and its FAQ says pgbouncer "might pose an issue if it's not done in 'connection' mode". It would need Neon's direct (unpooled) connection, which is workable but more fragile. context7 `/graphile/worker` (faq.md).
  - Rejected `bullmq` (6.7.2): it needs Redis, which is an extra Render Key Value service, cost and moving part. That is not justified for MVP volumes.
